# SDD Input Contracts Guide

## What a contract is

A **contract** is a piece of evidence provided by the user that states exactly the **requirements** — functional or technical — that a spec must satisfy in order for it to pass validation.

Contracts are **non-negotiable**. A contract that exists in `contracts.yml` is binding on the session. Any spec that does not account for every contract is incomplete.

## What a contract is not

- It is **not** an aspirational goal or "nice to have".
- It is **not** a guideline or best-practice document.
- It is **not** optional. If the requirement changes, the contract file or `contracts.yml` entry is updated or removed.

## Common contract types

There is no closed type system. Any artifact that expresses a hard requirement can be a contract. Common examples include:

| Category                      | Typical formats                                                  | Role                                                                                            |
| ----------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| API / Network contract        | OpenAPI (`yaml`/`json`), AsyncAPI, gRPC `.proto`, GraphQL schema | Defines request/response shape, status codes, validation rules                                  |
| UI / UX requirement           | Screenshot, Figma file, wireframe image, HTML prototype          | Defines layout, copy, interaction flow                                                          |
| SewingAI prototype            | HTML file generated by SewingAI                                  | Defines screen layout, DS component choices, visual interaction flow; binding on visible-UI ACs |
| Business rule                 | PDF requirement doc, Jira excerpt, signed-off PRD                | Defines domain logic, thresholds, compliance rules                                              |
| Data / Schema contract        | DDL, Avro schema, JSON Schema, database diagram                  | Defines persisted structure, migration constraints                                              |
| Security / Compliance mandate | Security review PDF, checklist, audit finding                    | Defines hardening rules, encryption, access control                                             |
| Performance / SLO target      | Benchmark report, monitoring dashboard screenshot                | Defines latency, throughput, error-budget thresholds                                            |

The `media_type` field in `contracts.yml` should describe the content accurately; it does not constrain the list above.

## Contract lifecycle in an SDD session

Contracts may be provided at any phase from **bootstrap through test-design** (i.e., up to but not including implementation). Once implementation begins, new contracts are treated as scope changes that require a new session or it may impact the existing track classification.

```
Phases where contracts may arrive:
  bootstrap ──► discovery ──► functional-spec ──► spec-validation
                                              ──► technical-plan ──► test-design
                                                                      │
                                                              implementation
                                                                      │
                                                              no new contracts
```

**At bootstrap:** contracts are captured in `contracts.yml` before any specialist work begins.

**During discovery / functional-spec:** the planner reviews contracts and maps each to at least one AC through `contract_mappings` in the minimal handoff. The mapping contains IDs only and does not alter Given-When-Then AC prose.

**During spec-validation / technical-plan / test-design:** if existing ACs already cover a late contract, the orchestrator records the relation with `contract-map` and continues without reopening. If the contract requires new or changed AC behavior, reopen `functional-spec` and re-run `spec-validation`.

### Late contract arrival protocol (test-design or earlier)

When a user provides a new contract after `functional-spec` has already passed:

1. **Capture** — add the contract to `contracts.yml` and the `contracts/` subdirectory.
2. **Assess impact** — determine whether existing AC behavior covers the contract or AC behavior must change.
3. **If fully covered by existing ACs:**
   - Run `contract-map` with the contract ID, registered spec path/scope, and affected AC IDs.
   - The command validates IDs and updates only Input Contract Trace; it does not advance or reopen a phase.
   - Record the late-contract decision in `sdd-state.yml.decisions[]` and continue the current phase.
4. **If new or changed ACs are required:**
   - Pause/fail the current gate and use normal reroute rules to reopen `functional-spec` when that phase is active.
   - If the active track skips `functional-spec`, treat this as a track/scope change and ask the user to start an appropriately classified session or keep the current one blocked.
   - Delegate the functional revision, accept its mapping-bearing manifest, and re-run `spec-validation` before resuming downstream work.
   - Record the reopening event in `sdd-state.yml.decisions[]` with rationale.
5. **Never silently absorb a late contract** — always validate traceability and, when needed, reopen the spec.

### Traceability rule

Every contract in `contracts.yml` MUST appear in `trace.md` under **Input Contract Trace** with:

- `Contract ID`: the `id` from `contracts.yml`
- `Path`: the relative path to the contract file
- `Affected ACs`: one or more `AC-N` identifiers from the approved spec
- `Evidence`: the source spec that owns the mapping; downstream test, implementation, and verification evidence remains linked through the mapped ACs
- `Added at`: the phase when the contract was captured (`bootstrap`, `discovery`, `functional-spec`, `spec-validation`, `technical-plan`, or `test-design`)

A contract without `Affected ACs` is an untraceable requirement and is treated as a spec-validation blocker.

### Unmappable contract handling

If a contract cannot be mapped to an AC during functional spec:

1. Record a stable blocker ID in a planner-owned artifact and reference that ID through the manifest's `blocker_refs`.
2. The planner does not silently drop contracts — they are mandatory requirements.
3. The orchestrator records the decision in `sdd-state.yml` `decisions[]` if the user explicitly removes the contract from scope.
4. If the user removes a contract, delete its entry from `contracts.yml`; do not retain historical rejected entries in the manifest. Contracts that do not exist must not be present in the SPEC.

## Specialist responsibilities

| Specialist                            | Contract responsibility                                                                                                                                                            |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AIDevPlanner` (functional-spec)      | Review all contracts; ensure each is reflected in draft AC behavior and declare contract/spec/AC IDs in `contract_mappings`; escalate unmappable contracts as referenced blockers. |
| `AIDevOrchestrator` (spec-validation) | Verify Input Contract Trace completeness; run deterministic cross-check between `contracts.yml` and `trace.md`. Handle contract arrivals per the contract arrival protocol.        |
| `AIDevTester` (test-design)           | Derive test evidence for ACs that carry contract links.                                                                                                                            |
| `AIDevCoder` (implementation)         | Implement such that the contract requirements are satisfied by the linked ACs.                                                                                                     |
| `AIDevVerifier` (spec-verification)   | Check that verification evidence covers contract-linked ACs and confirm that the produced artifact matches the contract evidence.                                                  |

## Validation rule for the orchestrator

Before advancing past `spec-validation`, the orchestrator must assert:

```yaml
gate_check:
  - for each contract in contracts.yml:
      assert: contract.id appears in trace.md Input Contract Trace
      assert: trace_entry.affected_acs is non-empty
      assert: every affected_ac exists in the stable spec
```

Failure of any assertion keeps the gate at `spec-validation` and blocks the session until the contract is mapped to an AC or explicitly removed from `contracts.yml` with a recorded decision.

`contracts.yml`:

```yaml
contracts:
  - id: "API-001"
    title: "User Service OpenAPI v3"
    path: "contracts/user-service-openapi.yaml"
```

```markdown
| Contract ID | Path                                | Affected ACs | Evidence                       |
```

## Summary

A contract is the **anchor of truth** that prevents the spec from drifting away from actual requirements. Every entry in `contracts.yml` is binding: trace it to acceptance criteria, and verify it at every gate.

# Late contract handling

(This handlers must only be followed by agents that are allowed to handle contracts as per the definition on this guide)

Contracts may be provided at any phase from **bootstrap through test-design** (i.e., up to but not including `implementation`). Once `implementation` begins, new contracts are treated as scope changes that require a new session.

When the user provides a new contract after `functional-spec` has already passed:

1. **Capture** — add the contract file to the `contracts/` subdirectory and its entry to `contracts.yml`.
2. **Assess impact** — determine whether existing AC behavior covers the contract or AC behavior must change.
3. **If existing ACs cover it**, use `contract-map` to add the ID-only mapping to Input Contract Trace and continue the current phase.
4. **If AC behavior must change**, reopen `functional-spec` when active, revise the specs, and re-run `spec-validation`. If the track skips that phase, treat it as a track/scope change rather than forcing an invalid reroute.
5. **Never silently absorb a late contract or hand-edit trace rows.** Use `contract-map` for mapping-only changes and functional revision for behavioral changes.

Reopening a phase is a state transition: clear any downstream phase completions that depend on the spec, preserve prior evidence where unchanged, and re-run the validation gate before resuming downstream work.
